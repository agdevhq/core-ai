<Update label="0.32.0" description="Per-message cache control on user and tool result messages" tags={["improvement"]}>
  ### @core-ai/core-ai

  - `UserMessage` and `ToolResultMessage` gain `providerOptions`, keyed by provider id, with the new `UserMessageProviderOptions` and `ToolResultMessageProviderOptions` interfaces for provider packages to augment.

  ### @core-ai/anthropic

  - User and tool result messages accept `providerOptions.anthropic.cacheControl` for explicit cache breakpoints with their own TTL. The breakpoint goes on the last content block the message produces. These breakpoints count toward the 4-breakpoint limit and the TTL ordering checks. A user message with `cacheControl` that is empty or ends with an empty text part throws `ValidationError`.
  - Serialize Messages API request bodies in a cache-friendly key order: `tools`, `system`, and `messages` come first, followed by per-request settings. Gateways that route prompt-cache lookups by the leading bytes of the body now see an identical prefix across turns.

  ### @core-ai/anthropic-vertex

  - User and tool result messages accept options under the `anthropic-vertex` key, including per-message `cacheControl`.
  - Improve prompt-cache hit rates on Vertex AI multi-region (`eu`, `us`) and `global` endpoints, which route requests by the leading bytes of the body.
</Update>

<Update label="0.31.0" description="System message placement capability and per-message cache control" tags={["breaking", "improvement"]}>
  <Warning>This release contains breaking changes to `@core-ai/core-ai`, `@core-ai/anthropic`, `@core-ai/google-genai`, and `@core-ai/google-vertex`.</Warning>

  ### @core-ai/core-ai

  - **Breaking:** `ModelCapabilities` gains a required `messages.systemPlacement` field (`'leading' | 'before-reply' | 'anywhere'`) describing where a model accepts system messages after the first non-system message. Custom `ChatModel` implementations and capability registries must add it.
  - Add `validateSystemMessagePlacement()`, which provider adapters run before every request and which throws the new `UnsupportedSystemMessagePlacementError`, and `getSystemMessagePlacementIssues()` to check a conversation without sending it. `validateMessages()` runs every message-level capability check in one call.
  - `SystemMessage` gains `providerOptions`, keyed by provider id.

  ### @core-ai/anthropic

  - **Breaking:** system messages are no longer joined into the top-level `system` prompt. Leading system messages are sent as one `system` text block each, which causes one cache miss on the first request after upgrading. On models that report `systemPlacement: 'before-reply'` (Claude Opus 4.8, Sonnet 5, Haiku 5.5 and later, and unrecognized model IDs), a later system message is sent in place. On earlier models, a later system message throws `UnsupportedSystemMessagePlacementError`.
  - System messages accept `providerOptions.anthropic.cacheControl` for per-message cache breakpoints with their own TTL. Requests that exceed 4 breakpoints, place a `1h` breakpoint after a `5m` one, or mismatch the TTL of a breakpoint on the last block throw `ValidationError` before the request.
  - Model ID aliases ending in `-latest` or `-0` now resolve to the capabilities of the model they point at, and the Vertex ID `claude-3-5-sonnet-v2` is recognized as Claude 3.5 Sonnet.

  ### @core-ai/anthropic-vertex

  - System messages accept options under the `anthropic-vertex` key, including per-message `cacheControl`. Claude Opus 4.8, Sonnet 5, Haiku 5.5, and later models accept a system message directly after a user or tool message.

  ### @core-ai/google-genai, @core-ai/google-vertex

  - **Breaking:** models report `systemPlacement: 'leading'`, and a system message after the first non-system message throws `UnsupportedSystemMessagePlacementError` instead of being merged into `systemInstruction`.

  ### @core-ai/openai, @core-ai/kimi, @core-ai/mistral, @core-ai/xai

  - Models report `systemPlacement: 'anywhere'`, and requests run the system message placement check. System messages are still sent where they appear.
</Update>

<Update label="0.29.0" description="maxTokens contract and output ceilings" tags={["breaking", "improvement"]}>
  <Warning>This release contains breaking changes to `@core-ai/anthropic`, `@core-ai/anthropic-vertex`, `@core-ai/google-genai`, and `@core-ai/google-vertex`.</Warning>

  ### @core-ai/core-ai

  - Define `maxTokens` as the total output allowance, covering reasoning tokens and the visible answer. An omitted `maxTokens` means the model's output ceiling, and adapters reject an explicit limit that cannot hold the reasoning budget of the requested effort instead of shrinking the budget.
  - Add optional `ModelCapabilities.output.maxTokens`, the verified output ceiling for a model ID.

  ### @core-ai/anthropic

  - **Breaking:** an omitted `maxTokens` uses `defaultMaxTokens` if you set it, otherwise the model's output ceiling (128,000 on Opus/Sonnet 4.6 and later, Fable, and Mythos; 64,000 on Claude 4.5), and 4,096 only for model IDs without a known ceiling.
  - **Breaking:** manual thinking budgets (Claude 4.5 and earlier) are no longer shrunk to fit `maxTokens`; a limit at or below the budget throws `ValidationError`. The `high` and `max` budgets are 50% and 75% of the model's output ceiling.
  - `generate()` and `generateObject()` stream internally and return the same result. Mid-stream errors such as `overloaded_error` surface as `ModelOverloadedError`, and aborts as `AbortedError`.
  - Keep redacted thinking blocks in streamed results, and report `output.maxTokens` for known Claude models.

  ### @core-ai/anthropic-vertex

  - **Breaking:** `defaultMaxTokens` no longer defaults to 4,096. Requests that omit `maxTokens` use the model's output ceiling, and manual thinking budgets throw `ValidationError` when `maxTokens` cannot hold them.

  ### @core-ai/google-genai

  - Use each Gemini 2.5 model's documented thinking budget range: `max` maps to the documented maximum (32,768 on Pro, 24,576 on Flash and Flash-Lite) and `high` to 75% of it.
  - **Breaking:** an explicit `maxTokens` at or below the Gemini 2.5 thinking budget throws `ValidationError` instead of returning an empty answer.
  - Report `output.maxTokens` (65,536) for known Gemini 2.5 and 3 models and `reasoning.thinkingBudgetRange` for Gemini 2.5.

  ### @core-ai/google-vertex

  - Re-export `GoogleThinkingBudgetRange`. Gemini 2.5 models use their documented thinking budget ranges, and an explicit `maxTokens` at or below the thinking budget throws `ValidationError`.
</Update>

<Update label="0.25.0" description="Per-tool strict tool schemas" tags={["improvement"]}>
  ### @core-ai/core-ai

  - Add per-tool strict tool schemas: `defineTool({ strict: true })` opts a single tool into provider-enforced schema adherence, `ModelCapabilities.tools.strictSchemas` reports model support, and strict tools are validated locally against the strict-capable schema contract (object root, closed objects, every key required, and the keyword subset every strict-capable provider accepts). Violations throw `ToolSchemaStrictnessError` with a `violations` list naming each offending schema path and a fix hint.

  ### @core-ai/anthropic

  - Strict tool schemas are now per-tool opt-in on Claude 4.5 and later models; previous releases marked every tool strict. The 20-strict-tool limit counts only opted-in tools, and discriminated unions (`oneOf`) are rewritten to `anyOf`. The internal `strictToolSchemasEnabled` factory option was removed.

  ### @core-ai/anthropic-vertex

  - **Breaking:** the `useStrictToolSchemas` option was removed. Strict tool schemas follow the per-tool opt-in and the underlying model capabilities. Vertex enforces the `structured_outputs` partner-model feature through your GCP organization policy.

  ### @core-ai/openai

  - Support per-tool `strict: true` on the Responses and Chat Completions APIs. Strict tools are sent with a normalized schema (`$schema` stripped, `additionalProperties: false` added recursively, `oneOf` rewritten to `anyOf`); non-strict tools keep the raw schema and carry an explicit `strict: false` on the Responses API. Models that predate Structured Outputs report strict schemas as unsupported through both APIs; unknown model IDs, including fine-tuned `ft:...` models, resolve optimistically to supported. The `strictToolSchemas`, `strictToolSchemasUnsupportedReason/Details`, and `disableParallelToolCallsWithStrictTools` factory options were removed.

  ### @core-ai/azure-openai

  - Support per-tool `strict: true` on the v1 (Responses) endpoint and on classic deployments with API version `2024-08-01-preview` or later; the `strictToolSchemasEnabled` deployment assertion was removed.

  ### @core-ai/openai-compat

  - Forward per-tool `strict: true` function tools with normalized schemas to gateways that implement OpenAI strict function tools; the `strictToolSchemas` endpoint assertion was removed.

  ### @core-ai/kimi

  - Forward per-tool `strict: true` function tools with normalized schemas.

  ### @core-ai/omnifact

  - Report strict tool schemas as supported and forward per-tool `strict: true` to the gateway with normalized schemas.

  ### @core-ai/google-genai, @core-ai/google-vertex, @core-ai/mistral

  - Report per-tool strict schemas as unsupported; a tool with `strict: true` throws `ToolSchemaStrictnessError` before any provider I/O.
</Update>
